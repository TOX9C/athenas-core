# Capability and Plugin Security Inventory

**Status:** Initial evidence inventory  
**Baseline date:** 2026-08-08  
**Scope:** macOS desktop renderer, plugin system, MCP/Agent Comms, and optional Mobile Mirror relay.

This is an implementation inventory, not a security certification. Findings are based on the current source tree and must be re-verified against the release candidate.

## Executive summary

- The Tauri command registry is internally consistent: **133 unique commands** are listed in both `src-tauri/src/main.rs` and `src-tauri/build.rs`.
- The generated permission directory now contains one allow permission file for each of the 133 registered commands after normalizing command underscores to permission hyphens. The stale `pty-listen-binary` artifact has been removed, and CI now checks for both missing and extra generated permissions.
- `src-tauri/capabilities/default.json` grants the main window the command-aligned custom permissions plus core/dialog/window/event/clipboard entries (the exact count is checked from the release candidate by the permission-drift script). It covers filesystem read/write, PTY/process control, LLM calls, browser child webviews, plugin host operations, and relay controls. The backend validators are therefore the primary security boundary; the capability is not least-privilege by feature area.
- The filesystem root resolver previously had a fail-open fallback to `/` in `effective_roots()`. The implementation gate now removes that fallback and accepts only a verified source-tree marker or standard macOS bundle `Contents/Resources`; the fix still requires release-artifact validation.
- The plugin crate validates manifest command/path fields and now bounds identifiers, config/event sizes, session counts, subscriptions, and pending message parameters; it also intersects session capabilities with manifest declarations and cleans sessions on disable/remove. The public release policy is now explicit in `PLUGIN_TRUST_POLICY.md`: trusted developer integrations only; no sandboxed third-party plugin ecosystem. Tauri renderer/plugin-host caller ownership remains a documented trusted-renderer limitation.
- Mobile Mirror has strong token generation/revocation and command/event allowlists, but it binds to `0.0.0.0` over plaintext HTTP/WebSocket and permits high-impact operations such as workspace file writes and PTY control. It remains **experimental, disabled by default, and excluded from public-launch scope** until its LAN threat model is explicitly accepted, tested, and documented by the release owner.

### Tauri capability configuration

`default.json` uses `core:default` and `dialog:default`, plus explicit window/event permissions and nearly the complete custom command surface. It also has `withGlobalTauri: true` in `src-tauri/tauri.conf.json`.

The production CSP is checked by `scripts/check-tauri-security-config.mjs`: scripts are restricted to `'self' 'wasm-unsafe-eval'`, connections to `'self' ipc:`, and debug WebDriver plus release relay autostart are source-gated. Inline styles and `data:`/`blob:` images remain intentional UI/asset allowances. Browser child-webview navigation parses and restricts URLs to HTTP(S) with a valid host, rejecting credentials, control characters, and non-web schemes. Exact signed-artifact CSP/rendering behavior and child-webview review remain release-candidate gates; CSP is not a substitute for command authorization.

**Finding C-1 — P2, accepted for this scope:** one default capability gives the main renderer access to all desktop features, including process control, filesystem writes, plugin state mutation, and secret-related commands. This release treats the bundled renderer as trusted and relies on hardened command handlers; broad shell-execute permissions are not granted. A future split between desktop, mobile, and privileged capabilities is recommended; do not reduce permissions blindly without verifying frontend callers.

**Finding C-2 — Resolved:** the stale `pty-listen-binary.toml` artifact was removed, missing capability entries were restored, and `check-tauri-permission-drift.mjs` is now part of CI. The check compares command-aligned generated permission stems and the default capability.

## 2. Filesystem boundary

All path-based filesystem commands inspected route through `validate_path_exists()` or `validate_path()`, which canonicalize request paths and compare them against the app root plus recanonicalized trusted roots. PTY cwd, search, swarm, and plugin discovery reuse this boundary. Native file dialogs are separate UI operations and must be reviewed independently.

**Finding F-1 — P0, implementation and focused regression tests complete; packaged-artifact validation pending:** The previous implementation constructed the roots list with:

```rust
get_workspace_root().unwrap_or_else(|_| std::path::PathBuf::from("/"))
```

If workspace-root discovery failed, `/` became an authorized root. The current implementation removes that fallback: resolution now requires either the source-tree marker or a standard macOS bundle `Contents/Resources` directory, and unknown layouts return an error. Focused backend tests cover resolver failure propagation and standard bundle-layout acceptance (`cargo test --manifest-path src-tauri/Cargo.toml commands::tests`). The remaining release gate is to exercise the exact signed/notarized artifact from Finder with an unrelated CWD and assert filesystem, plugin discovery, swarm, and PTY cwd operations reject when no valid root is available.

The `athena-store` snapshot persistence path now uses exclusive same-directory temporary files, durable file sync, atomic replacement, and (on Unix) parent-directory sync; it also serializes persistence and retains dirty state when a mutation races a flush. This closes the store's temporary-file/snapshot durability gap. Other filesystem write helpers still require their own packaged durability review. Path validation still occurs before later operations, so the release review must separately assess the remaining validation-to-operation TOCTOU window for every sensitive filesystem command and document the residual trusted-local-app threat model.

## 3. Plugin trust boundary

### Manifest and discovery

- `crates/athena-plugins/src/types.rs` defines plugin capabilities, MCP configuration, install methods, tools, event subscriptions, and config schemas.
- `crates/athena-plugins/src/discovery.rs` scans JSON manifests, limits each manifest to `MAX_MANIFEST_BYTES` (1 MiB), parses it, and calls manifest validation.
- `crates/athena-plugins/src/validation.rs` rejects absolute/traversal hook paths, shell metacharacters, non-whitelisted MCP command names/paths, and `PATH`/`HOME` overrides.
- `plugins/shared/setup.ts` writes `.claude/mcp.json` or `.opencode/mcp.json` and places `ATHENA_MCP_TOKEN`, host, port, and optional session ID in the configured MCP environment.
- The Rust plugin crate is a coordination/state layer; the bundled TypeScript setup code performs local config writes and connects to the loopback MCP server. A plugin is trusted code and can still use its own process/network/filesystem privileges once executed by the host/agent.

### Lifecycle and authorization

- `plugin_register` and `plugin_host_setup_plugin` construct a minimal manifest with empty permissions/capabilities and register it after validation. They do not install or sandbox a process.
- `enable_plugin`/`disable_plugin` change registry state and invoke callbacks. Disable/unregister now clean sessions, subscriptions, and pending messages, but the manager does not start/stop externally managed plugin processes.
- `register_session()` rejects disabled/error plugins, enforces the manager session cap, and intersects requested capabilities with the agent defaults and manifest-declared capabilities. Installed plugins remain compatible with the existing built-in host flow; a public untrusted-plugin policy still must not imply process sandboxing.
- `plugin_host_subscribe()` now checks session existence, plugin state, declared event subscriptions, and count/serialized-size limits. It still relies on the trusted Tauri renderer/host boundary for caller identity.
- `plugin_host_update_status()` and `plugin_host_unregister_session()` operate on supplied session IDs because the Tauri command API has no caller identity. This is an explicit trusted-renderer limitation, not an external-plugin authentication guarantee.
- `plugin_host_emit_event()` remains a trusted-renderer bridge and creates a source-less event for compatibility. Payload size is bounded at the command boundary; oversized manager events are rejected without callback/event emission. A caller-bound host-session API is still required before supporting mutually untrusted plugins.
- `plugin_get_config`/`plugin_set_config` remain registry-wide renderer operations; configuration input and merged stored values are bounded at 256 KiB. JSON-schema validation and per-plugin caller ownership are not implemented.

**Finding P-1 — P2/conditional, accepted for this scope:** plugin host operations remain trusted-renderer stateful APIs without caller-bound session ownership or schema validation. Enabled/disabled state, manifest capability intersection, event declarations, payload/config/session/subscription limits, disable/remove cleanup, and the explicit trusted-code policy are enforced. Public untrusted-plugin support remains out of scope until a caller-identity redesign and end-to-end policy test exist.

**Finding P-2 — P2, plugin lifecycle ownership is explicit but limited:** disable/unregister now remove sessions, subscriptions, and pending messages. The manager still does not own external MCP/plugin processes; plugins are trusted, externally managed clients and public docs must not imply process sandboxing.

**Finding P-3 — P2, accepted scope:** manifest validation permits a broad command whitelist (`node`, Python, shells, package runners, etc.) because plugins are trusted developer integrations. The public release does not advertise a marketplace, remote installation, provenance verification, or sandboxing. The policy and source check must remain green; expanding to untrusted plugins requires a separate security design.

## 4. MCP and Agent Comms

The MCP server binds to `127.0.0.1` in `crates/athena-core/src/mcp.rs`, requires an `initialize` request with a per-server token before other methods or broadcast registration, caps each line at 1 MiB, and closes idle connections after five minutes. Agent Comms is also loopback-bound and has an initialize-token gate plus bounded agent lines.

**Finding M-1 — implementation and repository regression tests complete; artifact evidence pending:** loopback MCP limits concurrent TCP clients, request rate, per-connection lifetime requests, line size, and idle time. Tests cover rate/lifetime budgets, per-connection authentication, malformed JSON parse errors, oversized-line disconnects, port conflicts, and shutdown. Stdio mode intentionally skips authentication because the parent process launches it and remains process-local. The release candidate still needs a clean packaged-artifact abuse soak and reviewer disposition.

## 5. Mobile Mirror relay

The relay implementation has meaningful controls:

- Token is generated as a UUID, stored in the OS keychain, validated as hex, and revoked on `relay_stop`.
- WebSocket upgrade requires the exact token-bearing subprotocol.
- Frames are capped at 64 KiB and event names are allowlisted.
- Terminal event forwarding applies pane/workspace filtering.
- The mobile command allowlist excludes API-key commands, trust-root changes, native dialogs, window controls, and most plugin mutation commands.

However, `src-tauri/src/relay/mod.rs` binds the HTTP/WS server to `0.0.0.0:8787`, and `command_allowed()` in `src-tauri/src/relay/dispatch.rs` permits `fs_write_file`, `pty_spawn`, `pty_write`, `pty_resize`, and `pty_kill`. The transport is plaintext HTTP/WebSocket, and the pairing token is the effective bearer credential.

**Finding R-1 — P1 if Mobile Mirror ships; P2 while excluded/disabled:** a LAN observer or malicious same-network peer may capture/replay the bearer token, then write trusted workspace files or control PTYs. The current launch decision is to keep Mobile Mirror experimental, disabled by default, and excluded from public-launch guarantees. If the scope changes, require explicit confirmation, TLS or a documented equivalent pairing channel, token rotation/revocation tests, client limits/rate limits, strict per-pane authorization, and a prominent trusted-LAN warning. The persisted `relay.enabled` setting records the last UI state but no longer causes auto-start on a normal public boot; only a debug build with `ATHENA_RELAY_AUTOSTART=1` enables development auto-start; release binaries compile this path out. The UI still provides explicit start/stop and token revocation.

## 6. Remediation order and release gates

1. **P0 first:** validate the fail-closed filesystem-root implementation against the packaged macOS artifact and add regression tests across every filesystem/cwd entry point.
2. **Before expanding plugin support:** keep the public scope limited to trusted developer integrations and document trusted-code execution. Do not advertise a marketplace, remote installation, provenance guarantee, or sandbox. A broader untrusted ecosystem requires P-1 caller identity, authorization/capability/schema controls, provenance, and process isolation before launch.
3. **Before enabling Mobile Mirror publicly:** resolve R-1 or exclude it from the release artifact/marketing scope; verify the normal public build cannot auto-start it when excluded. The current implementation requires an explicit debug-build-only autostart opt-in; release binaries compile out relay autostart.
4. **P2 hygiene in the same security pass:** split or justify the broad default capability; keep the command-aligned permission drift check green; and document CSP/default capability assumptions.
5. **MCP hardening:** add connection/rate budgets if local abuse is in scope; otherwise capture the local-trust assumption in user-facing security documentation.
